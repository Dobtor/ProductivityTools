# 需求符合性（對照主規畫書 §2.2）

階段 7 的產出（2026-10-09 全檔案深度稽核）。這份文件回答一個問題：
**規畫書寫的成功指標，今天達到了嗎？**

☠️ 它**不**修改規畫書。規畫書是計畫 artifact，不可被完工紀錄覆蓋。
這裡只放量測結果與落差。

## 先講最重要的一件事：需求與出貨路徑不對應

§2.2 的量化指標是為「**自寫 TS OOXML Parser ／排版引擎**」那條路線寫的。
而規畫書自己的 2026-10-09 狀態說明已經寫明：

> 兩條（`engine=ts` 後端 CLI、`importViaBrowserParser()` 瀏覽器）都還是
> **驗收通道**，使用者按「匯入」走的仍是 LibreOffice ＋ canvas-editor 的
> docx plugin。

所以：

| | 實際出貨的路徑 | §2.2 指標適用的路徑 |
|---|---|---|
| 管線 | docx → LibreOffice headless → HTML → canvas-editor | docx → OoxmlParser → layoutDocument → CanvasRenderer |
| 有量化驗收指標嗎 | **沒有** | 有（§2.2） |
| 有自動化回歸守衛嗎 | 有（78 步 tour ＋ 後端測試） | 有（VR pixelmatch） |

**出貨路徑沒有 §2.2 等級的量化驗收指標**。這不是缺陷，是現況——但它應該被
寫下來，而不是讓人以為 §2.2 的數字描述的是使用者按下「匯入」之後會發生的事。

## 逐條對照（§2.2 的指標 vs 實測）

| § 2.2 指標 | 要求 | 實測（2026-10-09） | 判定 |
|---|---|---|---|
| 真實樣本集 | 50 份台灣企業／政府 docx | **62 份**（9 個目錄；另有 290 支 LibreOffice 上游語料庫作廣域回歸） | ✓ 超過 |
| 內容保留（字元） | 100% | round-trip oracle（`OoxmlWriter`）有 65 支測試驗「AST → write → re-parse 資訊沒丟」 | ✓ 有守衛 |
| 結構保真（段落／表格） | 100% 正確 | 整合測試有 fingerprint 與 page-count baseline（`08_render_ops_trace`、`09_page_count_baseline`） | ✓ 有守衛 |
| **視覺差異（pixelmatch vs LibreOffice）** | **<2%** | per-page mean **7.89%**（worst 30.79%，42 fixtures／126 頁／0 failedPages） | **✗ 差約 4 倍** |
| 人工盲測 20 位 | 平均 >80% 分不出 | **沒有執行紀錄**（只在 sprint 日誌裡被提到過） | **✗ 未執行** |
| 頁面尺寸／邊界／分頁位置 | 100% 一致 | 只有整體 pixelmatch 與 page-count baseline，**沒有逐項量測** | **✗ 未逐項量** |
| 欄位寬度 | ≤5% 誤差 | 同上 | **✗ 未逐項量** |
| 行距／段距 | ≤2px 誤差 | 同上 | **✗ 未逐項量** |
| 字型／字重／字色 | 100% 正確 | 同上 | **✗ 未逐項量** |
| 表格合併（gridSpan／vMerge） | 100% 正確 | 有專門的 parser 測試，但不是「對比原檔」的量測 | ⚠️ 有測試、非量測 |
| 圖文繞排位置 | ≤10px 誤差 | `core/ooxml/layout/`（16 檔）**不可達**，ADR-034 的 `import` 軸宣告，附啟動條件 | **✗ 未接線** |

## ☠️ 閘門比需求鬆 2.5 到 25 倍

這是最容易誤導人的一點：

| 閘門 | 設定值 | §2.2 的要求 | 倍數 |
|---|---|---|---|
| `run_visual_regression.sh` 的 `MEAN_THRESHOLD` | 5% | 2% | 2.5× |
| `run_visual_regression.sh` 的 `WORST_THRESHOLD` | 10% | （§2.2 沒給 worst，但 mean <2% 隱含更嚴） | — |
| `visual_regression_v14.mjs` 的 `--max-diff` 預設 | **0.5（50%）** | 2% | 25× |

那些閘門的用途是「**不要退步**」——它們擋的是今天比昨天爛。
**它們不是 §2.2 的驗收門檻。** 兩者混為一談會得出「VR 綠了所以符合需求」
這個錯誤結論，而實際差了約 4 倍。

兩支腳本的檔頭已補上這張表（指回本文件），避免下一個人只讀閘門值。

## 所以「符合需求」嗎

**出貨路徑**：§2.2 沒有為它定指標，所以「符合」這個問題對它不成立。
它的保證來自 78 步 tour ＋ 646 則後端測試 ＋ 12 條完工判準（`DONE_CRITERIA.md`）。

**驗收通道（自寫渲染器）**：**不符合**。pixelmatch 差 4 倍、人工盲測未執行、
各維度公差未逐項量測、文繞圖那條甚至還沒接線。

要讓它符合，缺的不是程式碼量，是三件事（依代價排序）：
1. **逐項量測**取代整體 pixelmatch——現在只有一個總和數字，沒辦法知道 7.89%
   裡面有多少來自字寬、多少來自行距、多少來自文繞圖。沒有這個拆解，
   優化方向只能靠猜。
2. **把 `core/ooxml/layout/` 接上線**（ADR-034 的啟動條件：VR 出現 Word 文繞圖
   的 fixture 且現行 `core/layout` 量不出來）。
3. **人工盲測**——這件事需要 20 位真人，不是工程工作。

這三件都**不在本次稽核範圍**，列在 `AUDIT_LENSES.md` 的「還沒用過的尺」旁邊
作為需求層的待辦。
