# 最終優化建議（2026-10-09 全檔案深度稽核後）

這份文件是八階段稽核（1,140 檔逐一歸類）的最後產出。

**它刻意分三類，而且每一條都附代價與理由。** 「不該做」那一類跟「該做」一樣
重要——沒有它，下一個人會把已經決定不做的事重新提案一次（本模組的 CI 就被
提案過兩次）。

判斷依據一律是**量到的數字**，不是感覺。每條建議附上它所依據的量測。

## 可做（有價值，但代價或風險需要權衡）

### 1. `core/ooxml/layout`（16 檔／2,413 行）接上線 —— **優先序已下調**

ADR-034 的啟動條件是「VR 出現 Word 文繞圖的 fixture 且現行 `core/layout`
量不出來」。

**優化 2 量完之後：表格格線只佔誤差的 6.3%（0.50 pp）。** 圖片佔 28.9%，
但那是圖片本身的渲染／縮放／錨點，不等於文繞圖——要先把這兩者分開，
條件才算成立。

所以這一條從「等條件成立」變成「**先做更細的圖片誤差分類**」。

**代價**：高。活的 layout 是 `core/layout/`（12 檔／4,485 行），兩套並存，
接線等於選一套並遷移。

### 2. `SPRINT_AUDIT_CONSOLIDATED.md`（42,899 行）分檔

**量測**：它佔兩模組全部文件行數的 **83%**（42,899／51,506），而且是
`test_doc_links.py` 唯一豁免的檔案——它提到 12 個已不存在的檔名，
而那些提及是它的工作（歷史日誌）。

**好處**：分檔後連結檢查能覆蓋它；單一巨檔讓「這段歷史在哪」很難定位。
**代價**：中。
**風險**：失去「一個檔案 grep 完所有歷史」的便利——這一輪稽核就用了好幾次。

**我的判斷是先不動**：它的缺點（巨大）是已知且可忍受的，優點（可搜尋）
在稽核時反覆發揮作用。若哪天要把它對外公開再說。

## 不該做（有明確理由）

| 項目 | 為什麼不做 |
|---|---|
| **接 `core/ooxml/worker`**（17 檔／2,382 行） | 它自己的檔頭就寫 Sprint 197 final audit 判定「不建議」（cost/benefit marginal、cache 五連發已 ~10× warm path 加速、真實文件只有 20–50 頁），是 explicit OVERRIDE 之下做出來的 SPIKE-only。使用者 2026-10-09 明確指示「留在 dobtor_doc_import，**先不接**」。留著是因為它有 51 支測試記錄了設計意圖。 |
| **GitHub Actions CI** | 做過又當天撤掉（ADR-028）。使用者：「ci 的設計都拿掉，不做」。 |
| **git pre-push hook 跑 `make done`** | 使用者 2026-10-09 指示「拿掉」。`make done` 本身他要，**什麼時候跑是他決定的**。這兩條合起來的意思是「不要任何自動化閘門」。 |
| **i18n string sweep（把中文包 `_()`）** | `docs/a11y_i18n_design.md` 明訂「預設語系 zh_TW、hardcode 中文是刻意的」，完整 sweep 等英文需求出現。那是決定，不是缺口。 |
| **把 VR 閘門從 5%／10% 收緊到 §2.2 的 2%** | 會**立刻全紅**（實測 7.89%）。閘門的用途是「不要退步」；收緊它不會讓品質變好，只會訓練大家無視紅燈——那正是本次稽核一路在反對的事。要符合 §2.2 要走「該做 2 → 可做 1」那條路，不是改閘門。 |
| **把 fixtures 搬到 git-lfs** | **被數字否決**：磁碟上 134MB，但整個 repo 的 pack 只有 **17.99 MiB**——docx/png 壓得很好。git-lfs 會換來 clone 依賴與工具鏈複雜度，解決一個不存在的問題。 |
| **`/dobtor/fonts/*` 的 `csrf=False` 改掉** | 兩條路由都不改變任何狀態（一條 GET 字型、一條只讀清單），CSRF 對它們沒有意義。動它只增加破壞既有行為的風險。 |
| **降版 migration（18.0.15.2.0 → 更舊）** | 沒有降版需求，Odoo 本身也不支援。 |
| **刪掉 `core/ooxml/export`（OoxmlWriter，2 檔／2,297 行）** | 我在 2026-10-09 判過它「可刪」，**那是錯的**：它是 **65 支測試的 round-trip oracle**（AST → write → unzip → re-parse → 驗證資訊沒丟），是證明 parser 真的留住 Word 資訊的工具。ADR-034 把它標為 `tooling` 軸，「這一條永遠不會接上線，不要再把它當孤兒」。 |

## 這份文件怎麼用

1. 想知道「現在完成了嗎」→ `make done`（12 條判準，`DONE_CRITERIA.md`）
2. 想知道「還有什麼沒查」→ `AUDIT_LENSES.md` 的「還沒用過的尺」
3. 想知道「下一步做什麼」→ 這份文件的「該做」，按編號順序（2 是 3 以外其餘的前置）
4. 想提案某件事 → **先查「不該做」那張表**。表上有的，除非你帶著新的量測
   數字來推翻它的理由，否則不要重新提案。
