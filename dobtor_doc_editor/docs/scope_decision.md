# 文件產製通路選擇決策（W5-6 P1-3）

**狀態**：W5-6 補強衝刺實作  
**對應漏項**：P1-3 — 與既有 QWeb PDF 報表共存策略缺  
**完成日期**：2026-05-06

---

## 1. 為什麼需要這份決策

ChienYi 系統內**兩條文件產製通路並存**：

| 通路 | 已落地報表 |
|---|---|
| **QWeb PDF 報表**（既有） | 通報單、估驗單、施工日誌（單張+批量）、自主檢查表 |
| **dobtor_doc_editor**（補強衝刺中） | 開發中 |

如果不講清楚邊界，會發生：
- 工程師不知道新功能該用哪條 → 兩邊都做半套
- 使用者面對「同樣的監造會議，到底用 QWeb 還是 dobtor？」不知所措
- 維護成本翻倍（兩邊都要改）

## 2. 核心決策樹

```
新文件需求進來，先問三個問題：

Q1：這份文件「需要人工編輯內容」嗎？
  ├─ 否（系統自動產出）  → 用 QWeb
  └─ 是                  → Q2

Q2：這份文件「需要多人線上協作」嗎？
  ├─ 否（單人填表簽核）  → 用 QWeb（簡單表單已能應付）
  └─ 是                  → Q3

Q3：這份文件「版面複雜度高」嗎？（含表格嵌套、圖片繞排、頁首頁尾不同節）
  ├─ 否                  → 兩者都可，看團隊熟悉度
  └─ 是                  → 用 dobtor_doc_editor
```

## 3. 詳細決策表

| 文件特性 | 用 QWeb PDF（既有） | 用 dobtor_doc_editor |
|---|---|---|
| 系統自動產出、無人工編輯（月報、列印單據） | ✅ | ❌ |
| 範本欄位固定、需簽核（通報單、估驗單、施工日誌、自主檢查表） | ✅（保留現狀） | ⚠️ 短期不取代 |
| 需多人協作、版面複雜、現場需編輯（監造會議記錄、施工計畫書） | ❌ | ✅ |
| 需法定固定格式（政府公文、報部資料） | ✅ | ❌ |
| 需即時填表 + 可追蹤版本歷史 | ❌ | ✅ |
| 客戶/承包商要在線上看 + 編輯（portal user） | ❌ | ✅（W2-3 已支援） |
| 需 docx 雙向 round-trip（編輯後匯出 docx 仍可在 Word 開） | ❌ | ✅（Phase 6 完成後） |
| 大量批次列印（一次列印 100+ 份） | ✅ | ❌ |

## 4. 引用規則（給工程師看的硬規則）

### 4.1 不做的事

1. **不要把既有 QWeb 報表搬到 dobtor**：
   - QWeb 已穩定、批量列印優、模組職責清晰
   - 搬遷成本高、收益低
   - 例外：使用者明確抱怨某報表「我想要在線上微調再列印」 → 才考慮

2. **不要在新模組同時做兩條通路**：
   - 如果某個業務場景定義不清，先用 QWeb（投入成本低、容易先上線）
   - 確認需要協作再轉 dobtor

3. **不要在 dobtor 裡複製 ChienYi 業務邏輯**：
   - dobtor_doc_editor 只負責「文件本身」（內容、樣板、編輯、版本）
   - ChienYi 業務邏輯（工項、估驗、缺失關聯）由 mixin 帶入，不在 dobtor 模型內複製欄位

4. **不要在 dobtor 裡追蹤或指使別的 repo**（2026-10-09 加）：
   - 不要在註解／文件裡列出其他模組的檔名、模型清單或「他們還要改什麼」
   - 不要把別的 repo 的待辦寫進這裡——那份清單一定會過期，而且沒有人會來更新它
   - 需要說明「這支方法本模組內沒有呼叫者但不能刪」時，講**規則**而不是講對方：
     「這是給整合模組用的公開 API，死碼稽核的判斷依據是本模組**之外**有沒有
     引用」——而不是「某某模組的某某測試在用它」
   - 這一條是從實際違規補上的：刪 `_doc_render_context()` 時我在 mixin 的註解
     與整合文件裡點名了另一個模組的 6 個模型、還寫了「要在那個 repo 清掉」。
     那讓 dobtor 的程式碼持有對方的內部狀態，正是第 3 條想避免的事的另一種形式。
   - 例外：**舉例**可以（「如 ChienYi 承包商」、以某個模型示範怎麼整合），
     以及以來源命名的測試 fixture。差別是「舉例」不會過期，「追蹤狀態」會。

### 4.2 要做的事

1. **整合走 mixin**：
   - 任何 ChienYi 模型若要關聯 dobtor 文件，inherit `doc.linked.mixin`（W5-6 提供）
   - 不要在 ChienYi 模型直接寫 `doc_id = fields.Many2one('doc.document')`

2. **新需求先填這份決策樹**：
   - 在 PR description 中標註「為何選 X 通路」
   - 確認 reviewer 同意

3. **跨通路引用要用清楚的命名**：
   - QWeb 模板：`report_<功能>` 或 `<功能>_report`
   - dobtor 樣板：`doc.template` record 的 `name` 欄位用「<功能>樣板」

## 5. 已知不確定區的處理

某些文件在邊界上，先列出共識：

| 文件 | 目前通路 | 何時可能轉換 |
|---|---|---|
| 監造會議記錄 | dobtor（W5-6 整合） | 已決 |
| 施工計畫書 | dobtor（規劃中） | 待 W11+ Phase 1 OOXML 補完後啟用 |
| 缺失改善通知書 | QWeb | 若需照片現場標註才轉 dobtor |
| 估驗計價單 | QWeb | 不轉（金額計算與 ERP 工項強耦合） |
| 通報單 | QWeb | 不轉（簽核流程已穩定） |
| 自主檢查表 | QWeb | 視 W11+ 後是否需「線上多人協作填表」決定 |
| 工程紀錄 / 工作日誌 | QWeb | 不轉 |

## 6. 例外覆核流程

如果有需求覺得「我的場景上述決策樹答不出來」，覆核流程：

1. 在 PR description 寫場景與兩條通路的權衡

## 7. 特殊案例記錄

（依需求填入）

| 日期 | 案例 | 決策 | 理由 |
|---|---|---|---|
| 2026-05-06 | 初版決策樹 | 訂出 §3、§4 規則 | 補強衝刺 W5-6 P1-3 |
| 2026-10-08 | **QWeb 報表 → 範本轉換器**（`doc.qweb.converter`） | 做，但只做「**轉換工具**」，不搬遷既有報表 | §4.1 第 1 條的例外條款：「使用者明確抱怨某報表『我想要在線上微調再列印』→ 才考慮」。轉換器把原生 arch 轉成 `doc.template`，讓使用者自己決定要不要用；原生報表完全不動，兩條通路仍然並存。覆蓋範圍與刻意不支援的項目見 [qweb_converter_coverage.md](qweb_converter_coverage.md) |

> **§4.1 第 1 條仍然有效**：轉換器的存在不代表「把報表都搬過來」。
> 它是給「某一張報表確實需要線上微調」的那個例外用的工具，
> 轉完的範本與原生報表各自獨立。
>
> 「不會自己生效」靠的是**兩道**預設，不是模型的 `active` 預設
>（`doc.report.active` 預設是 `True`——手動建一筆綁定就是明確的動作，
> 那時立刻生效才對）：
>
> 1. 精靈的「同時建立報表綁定」預設**不勾**（`create_binding = False`）
> 2. 真的勾了，建出來的那一筆帶 `active=False`，並在待辦清單寫明
>    「已建立報表綁定但停用中」
>
> 2026-10-08 在報表表單、報表清單齒輪與 qweb 範本表單加了「轉成列印範本」
> 入口，那只是把精靈變得找得到，上面兩道預設沒有改——所以政策不變。
