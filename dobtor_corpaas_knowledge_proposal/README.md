# dobtor_corpaas_knowledge_proposal — 服務建議書／評估報價／預估成本

CorPaaS 方案知識核心（`dobtor_corpaas_knowledge`）的出口三。規格：
`dobtor_corpaas_knowledge/IMPLEMENTATION_SPEC.md`「模組 C」。

## 流程

1. **痛點**：手動輸入，或「匯入痛點」上傳售前 xlsx。每張部門表第 1 列標題、第 2 列表頭、第 3 列起資料
   （`# | 客戶提問／痛點 | 現況說明 | 解決方案 | 現有 or 客製 | 對應原生功能／模組 | 報價重點`）；
   只匯入表頭有「痛點／客戶提問」與「現有 or 客製」欄的部門表（總覽及其改名、彙總、待確認事項、
   解決方案總表、延伸分析表都略過；表名含「總覽／彙總／總表／待確認事項／延伸」也略過）。
   以一般模式載入（不用 read_only），往下合併的「#／痛點」併成一筆痛點，其他欄位換行串起來。
   四色 🟢原生 🔵Dobtor現有 🟠客製微調 🔴客製開發 ⚪沿用現況；⚪待確認＝不給顏色（要判斷，不能當沿用現況被排除）；
   🟣企業版（Enterprise 專屬）＝客製（CorPaaS 是 CE）。組合標籤取最先出現的顏色。
2. **AI 比對能力**：痛點＋方案能力（pain/outcome/color/可用性）→ 對應提議（四色、客製參考人天區間寫進說明）。
   按鈕排入佇列（`corpaas.knowledge.ai.enqueue(self, '_ai_match_run', package)`），完成或失敗寫在紀錄裡。
   重跑只取代「未確認的 AI 提議」。能力在方案裡是 addon 時帶入**所有**缺的模組產品（同分支優先；可單賣但沒產品的列在說明）。
3. **計算估算**：只算「已確認且非沿用現況」的對應。每個能力取它的工時範本（能力 × 工項），
   再加通用工項（範本 capability 空白，每張一次）：
   `days = base_days + ceil(driver_qty / unit_size) × per_unit_days`。
   驅動量取自建議書欄位（公司數、使用者數、角色數、串接數、訓練場次），`records_100` 取資料移轉檢核表
   該能力主資料模型的筆數 ÷ 100。檢核表模型＝情境 `seed_models()` ∪ 能力 `master_data_models`。
   設定微調：能力有工時範本就只用範本（不再疊 AI 區間中位數）；沒有範本才取中位數。客製開發一律取中位數另計。
   `records_100`：能力沒宣告主資料模型時，退回情境示範資料的模型。
   工項分類沿用 CBMC：需求設定／資料移轉／教育訓練／上線部署／專案管理。
4. **建議書**：痛點對應表、方案能力（裝了行銷模組就用 pitch 的**核准上線快照** `_live()`，不讀草稿欄位；
   否則能力 pain/outcome）、報價表（加購模組每列金額＝合計用的首年金額）、
   資料移轉檢核表；只用 Bootstrap 5／snippet class。可列印「服務建議書」與「內部成本頁」PDF。
5. **建立報價單**：方案變體一行（`package_tier`、`concurrent_users`、`storage_gb`、`committed_*`，
   價格由 dobtor_corpaas_sale 的 `_compute_price_unit` → `compute_package_price` 算）、加購模組各一行、
   每筆估算明細一行「導入服務（人天）」產品（數量＝人天、單價＝日費率）。方案變體取自方案套件
   （套件指定變體優先；週期兄弟只在同 branch_name 找）。
   **不自動開通**：訂單記 `knowledge_proposal_id`、`knowledge_provision_state='hold'`，不標 `is_to_create_paas`；
   覆寫 `sale.order._maybe_provision_by_tier()`（`action_confirm` 對每張單都呼叫它）→ 擋下並留言。
   業務按「確認開通」（`corpaas.knowledge.provision.wizard`，繼承 `corpaas.order.wizard` 的欄位與
   new／stack／change_tier 三種模式）：報價階段把模式寫到這張單（確認時照常走開通／疊加／換層級鏈）；
   已確認的單只能放行為新平台（疊加與換層級的計價不同）。客戶已有平台時模式不給預設，必須明確選。
6. **送出**：寫入 `snapshot_json`（能力、敘事、工項、價格、成本、HTML），之後建議書與痛點／對應／估算／
   檢核表一律唯讀（`write()` 擋）；只能改狀態（成交／未成交）、連報價單、工時回寫時間。要改就「複製新版」。
   送出後金額與成本欄位（stored compute）一律從快照讀，工時回寫校正範本、設定調價都不會改到。
7. **工時回寫**（需 hr_timesheet）：讀報價單關聯專案的 timesheet，以工時說明＋任務名稱（依空白與括號標點斷詞）
   ＋任務標籤（整個標籤一個詞）**整詞**比對能力 code 與工項（代碼、中文名或別名）；沒有能力 code 的工時不列入
   （通用工項要明確標「通用」），同一筆寫了兩個工項也不列入。小時 ÷ 每人天工時＝實際人天；反推基礎人天（扣掉驅動量那段）後以
   簡單移動平均（種子＝初始 base_days，視窗見設定）更新 `base_days`，留下校正歷史。同一建議書對同一範本只校正一次。
   ★ 專案結案自動回寫：本模組不依賴 `project`，自動觸發在橋接模組
   `dobtor_corpaas_knowledge_proposal_project`（auto_install，depends 本模組＋sale_project＋hr_timesheet）：
   專案 `stage_id` 進到摺疊（fold）階段時對關聯建議書呼叫 `action_feedback_actuals()`，失敗只留言不擋結案。
   沒裝橋接模組（或沒開專案階段）時仍用手動按「工時回寫」。
8. **成本與毛利**（首年）：`internal_cost = Σ 人天 × 內部人天成本 ＋ 12 × (基礎設施 ＋ 第三方 ＋ AI 點數)`。
   基礎設施＝CCU × 每 CCU 月成本（共享層且裝了 dobtor_infrastructure_cost、環境成本可信時用
   `infrastructure.environment.cost_per_ccu`）＋ 能力資源特徵（`storage_per_record_kb` × 筆數 → GB × 每 GB；
   `extra_worker_mb` ÷ worker MB ＋ `heavy_cron` 半個 worker → × 每 worker）＋ 儲存 GB × 每 GB。
   任一來源是估的（資源特徵沒標 `"calibrated": true`、工時範本未校正、主機成本用設定值、第三方沒寫金額）
   → `cost_is_estimate`，成本頁標「估算值」並列出原因。

## 訂閱價格

不自己算：`product.template.compute_package_price(tier, concurrent_users, committed_qty, storage_gb,
cycle, committed_usage)`（dobtor_corpaas_product）。週期取方案變體的 `recurring_rule_type`（有週期變體時先用
`_corpaas_cycle_variant()` 挑），與 SO 行 `_paas_cycle()` 同一來源；首年＝`cycle_total × 12 / months`。
加購模組以產品牌價估（訂閱產品依 `recurring_rule_type` 換算成一年）。

## 權限

- 業務（`sales_team.group_sale_salesman`）：建議書全權、工時範本／校正歷史唯讀、能力／情境唯讀；
  入口在「銷售 › 訂單 › 服務建議書」。
- 知識編輯：另可維護工時範本、執行工時回寫；入口在「方案知識 › 出口 › 建議書」。
- 知識管理：可刪工時範本與校正歷史。

## 設定

設定 › CorPaaS 基礎設施 › 方案知識區塊下方「服務建議書」：日費率、內部人天成本、導入服務產品、
每 CCU／GB／worker 月成本、第三方預設月費、每 AI 點成本、每人天工時、移動平均視窗。

## 2.0：案件、版本與文件輸出

### 案件與版本（`models/case.py`）

- **案件**（`corpaas.knowledge.case`，編號 `CAS/年/流水號`）管「這個客戶這件事」；**版本**＝既有的建議書
  （`corpaas.knowledge.proposal`，沒改名，避免大遷移）管「某一次送出的內容」。每份建議書屬於一個案件，
  建立時沒指定會自動開一個。
- 版號 `v主.次`：「複製新版」次版 +1（v1.0 → v1.1），「重大改版」主版 +1（v1.3 → v2.0）；一律以案件裡
  **已有的最大版號**往後接，不會出現兩個 v1.1。`supersedes_id` 記前一版。
- **一個商機可以有多個案件**（追加報價、分階段各一案）；追加案用 `parent_case_id` 指向原案。
- 提案**直接依賴 `sale_crm`**：建報價單帶 `opportunity_id`（sale_crm 的收入回填與
  `dobtor_mail_activity_crm` 的「專案回寫商機」才接得起來）；送出時商機留言，並（可關）把
  「所有未失敗案件、客戶手上那一版」的報價合計寫進預估收入。成交／未成交**只留言**，
  從不自動搬商機階段、不標成交／失敗。
- 舊資料遷移（`migrations/18.0.2.0.0`）：沒有案件的舊建議書各自升為一個案件的 v1.0。
  ☠️ 不用「同客戶」猜哪些是同一案件 —— 以前的「複製新版」沒有記錄版本關係，拆開比併錯容易修。

### 版本的組成（`models/version_parts.py`）

報價規格書每一份都有、而以前的建議書沒存的東西，現在都是**版本資料表**；文件只是它們的投影：

| 資料表 | 對應規格書的章節 |
|--------|------------------|
| `basis` 報價基礎 | 封面「報價基礎：貴公司 2026-08-31 提供之…」 |
| `change_line` 需求核對與本版處理 | 「貴公司最終核對之剛需／本版處理／對應章節」 |
| `scope_item` 範圍界線 | 涵蓋／不涵蓋（另行估列）／排除（不建議開發）／選配 |
| `obligation` 前提與客戶配合事項 | 導入前提、客戶須提供的資料 |
| `phase` 導入階段 | 階段／內容／期間／工時／里程碑（WBS 的家） |
| `acceptance_unit` 驗收單元（預算大類） | 預算大類／驗收標準／工時／占比／金額 |
| `payment_term` 付款款別 | 動員款／各單元驗收款／時點／比例／金額 |
| `clause_line` ← `clause_template` 條款庫 | 備註與免責 |
| `benefit_item` 效益評估 | 作業項目／現況人工／導入後／年化節省（假設） |

- **工時制固定預算**（`pricing_model = time_budget`）：沒有訂閱與加購、沒有我們代管的主機成本；金額＝工時 ×
  每小時費率（留空取 日費率 ÷ 每人天工時）。驗收單元的金額依其涵蓋的估算明細歸屬，**沒歸屬的明細
  （專案管理等）依各單元直接工時比例攤**，所以不論怎麼歸類，各單元金額加總＝總額。款別預設
  「動員款 30% ＋ 各單元驗收 70%」。報價單沒有方案行、`knowledge_provision_state='none'`（不需開通）。
- **版本差異草稿**（`services/versioning.py`）：從前一版的**凍結快照**算出痛點新增／移除／對應變更、
  金額與人天變動，當成「本版處理」的起點；只取代「版本差異」來源的列，手動輸入的客戶核對項不動。
- 全部子表繼承 `corpaas.knowledge.proposal.child`：送出後寫／建／刪都擋；快照涵蓋所有組成。
- 複製新版：報價基礎、範圍、前提、階段、單元、款別、條款、效益帶到新版（款別的基準單元會對回新版自己的單元）；
  **需求核對不繼承**（每一版自己的客戶核對）。

### 條款庫（`data/clause_data.xml`）

從 8 份既有報價規格書歸納（以賽亞 v2.0、預建 v6、SKF 7.4、極電 BYOD v1.0、蔦燒 V2、永然 V1、大中和 v2、
CBMC V3）：**只收跨文件重複出現、且不含客戶專屬資訊的通用條款**，共 35 條、其中 29 條啟用。
每條記來源（出現在哪幾份）與適用條件（一律／訂閱／工時制／含客製／含資料移轉／含串接／多公司）。
變數 `{validity_days}`、`{warranty_months}`、`{payment_days}`、`{acceptance_days}`、`{payment_summary}`、
`{hourly_rate}`… 載入時換成這個版本的值（設定頁可調預設值）；**不認得的變數原樣留著**，缺值看得見。
法務性質的承諾（責任上限、資料保存／銷毀年限、終止交還、資料所有權）**預設停用**，法務確認後再啟用。
☠️ 資料檔是 `noupdate`：客戶改過的條款不會被升級蓋回去；要改出貨內容請寫 migration。

### Word／PDF 輸出（`models/proposal_doc.py`、`services/doc_template.py`）

- 直接依賴 `dobtor_doc_editor`。範本（`doc.template`）綁在提案**既有的列印動作**上（`doc.report`），
  使用者按的還是原本的「列印」；停用那筆綁定就退回原本的 QWeb 報表。
- 範本只讀 `doc_report_values()` 回的 `data.*`：**已送出的版本讀凍結快照**，所以不論之後能力文案、工時範本、
  牌價怎麼變，同一版重新輸出得到的永遠是送出時的那份；草稿讀現場資料。
- 章節編號動態給（一、二、三…），**沒有資料的章節整章消失**、編號仍連續。
- 「下載 Word」按鈕（`action_download_word`）：輸出 DOCX 並用 `services/docx_polish.py` 補上表頭／交錯底色與框線
  （doc_editor 的轉換器不支援儲存格底色）；每次下載留一筆 `doc.output`。
- ☠️ **DOCX 是 doc_editor 的「匯出去編輯」便利功能，不是正式輸出**（經 python-docx 轉換，無法保證與畫面一致）；
  正式交給客戶請用 PDF。
- ☠️ **範本寫法的兩個坑**（都不會報錯、只會少印東西）：
  1. 段落的邊界是換行元素，表格不是。表格後面緊接條件段落，兩者會被當成同一個段落 —— 條件為假時
     連前面那張表一起消失。`doc_template.separate_tables()` 在每張表後補換行。
  2. 沒資料的章節要「標題段落 ＋ 表頭列」各放一個條件標記，只拿掉標題的話會留下只有表頭的空表格。
- ☠️ 不要照抄 ChienYi 整合的 `_doc_render_context()`：doc_editor 的文件已註明那個機制從來沒生效。
- 已知限制：能力章節是「能力層級」的表（能力／痛點／成果／分類），尚未做「能力 → 功能項」兩層；
  新版範本不會覆蓋已存在的範本（客戶可能改過版面），要用出貨版面重建請呼叫
  `_ensure_doc_template(force=True)`。

## 商機的「會議與筆記」（2.0.x）

* 商機表單新增「會議與筆記」分頁：「選擇會議與筆記」精靈預設帶出行事曆事件掛在此商機的會議記錄，
  也可加入其他自己看得到的筆記。每筆有角色（客戶提供／內部討論／補充）、是否列入報價基礎、備註。
* **內部討論預設不列入報價基礎**（可能含底價、成本），可手動勾選。
* 不放寬 `note.note` 的讀取規則；連結時把標題、日期存在連結列，筆記能不能點開仍由原規則決定。
* 新建版本（含複製新版）會自動把列入的來源與商機附件補進「報價基礎」（只放標題與日期，不放內容）；
  「從商機帶入會議與附件」按鈕可手動補。
* 內容指紋：筆記帶入後被改過，報價基礎標示「內容已更新」；新版另標「本版新增」，
  「以前一版產生差異草稿」會把這兩種寫進需求核對。按帶入按鈕即視為已看過、更新指紋。
* 筆記改名：按帶入按鈕時，連結列與沿用舊標題的基礎列一起改名。
  「帶入並移除商機已不列入的來源」另外刪除已取消列入／已刪除的來源列（手動列不動）。
* **AI 從會議筆記萃取痛點**：只讀勾了「AI 可讀」的來源（內部討論預設不勾，單篇 6000／總量 20000 字截斷），
  排入佇列、新痛點標「AI 自筆記萃取」並自動去重。★ AI 讀取不受筆記「只能看自己的」規則限制，
  有人連結並勾選即視為授權。
* **由對應產生範圍草稿**：確認且方案現有的能力→涵蓋；需加購→選配；沿用現況／未確認／方案不含→不涵蓋。
  已有範圍列時不動作。
* 送出快照的報價基礎帶內容指紋，可稽核當時依據的筆記版本。
* 依賴 `dobtor_meeting_minutes`。
